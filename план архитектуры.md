# Telegram Course Bot Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL at execution time: use `superpowers:subagent-driven-development` or `superpowers:executing-plans`. This plan is for a greenfield repo in `/Users/asmtv1/Desktop/tgbot`.

**Goal:** Build a TypeScript monorepo where a Telegram bot sells a video course through YooKassa, access is granted only after verified payment, and a Telegram Mini App shows protected Kinescope lessons.

**Architecture:** `apps/api` owns payments, access, Telegram auth, course data, and DB writes. `apps/bot` and `apps/miniapp` are clients of the API. `packages/db` owns Prisma/PostgreSQL. `packages/shared` owns shared types/contracts only, not business logic.

**Important compliance note:** Telegram’s current official docs say digital goods/services sold inside Telegram apps must use Telegram Stars (`XTR`), not third-party providers. The v1 below implements the YooKassa flow you requested, but the payment boundary must stay provider-shaped so a Stars provider can be added or swapped before public launch if platform compliance becomes the priority.

Verified API facts to implement against:

- YooKassa API endpoint is `https://api.yookassa.ru/v3/`, with HTTP Basic Auth using shop id + secret key. Use direct `fetch`, not a random SDK. Source: [YooKassa interaction format](https://yookassa.ru/developers/using-api/interaction-format).
- YooKassa payment creation uses `POST /payments`, `Idempotence-Key`, `amount`, `capture: true`, `confirmation.type: redirect`, `return_url`, and `metadata.order_id`. It returns `confirmation.confirmation_url`. Source: [YooKassa payment process](https://yookassa.ru/developers/payment-acceptance/getting-started/payment-process).
- YooKassa webhook must return HTTP 200; non-200 responses are retried for 24 hours. Verify webhook authenticity by fetching the payment status from YooKassa and optionally checking source IP. Source: [YooKassa webhooks](https://yookassa.ru/developers/using-api/webhooks).
- Telegram Mini App must send raw `Telegram.WebApp.initData` to backend; `initDataUnsafe` is not trusted. Validate with HMAC-SHA-256 and `WebAppData`. Source: [Telegram Mini Apps validation](https://core.telegram.org/bots/webapps).
- Telegram bot production webhook should use `setWebhook.secret_token`; validate `X-Telegram-Bot-Api-Secret-Token`. Source: [Telegram Bot API setWebhook](https://core.telegram.org/bots/api#setwebhook).
- Telegram Web App button uses `web_app: WebAppInfo` and works in private chats. Source: [Telegram Bot API KeyboardButton](https://core.telegram.org/bots/api#keyboardbutton).
- Kinescope API uses Bearer access token, has `/v1/videos`, `/v1/players`, `/v1/privacy-domains`, and `/v1/drm/auth`. Source: [Kinescope API Postman docs](https://documenter.getpostman.com/view/10589901/TVCcXpNM). For v1, videos are uploaded/configured in Kinescope dashboard; app stores `kinescopeVideoId` and `kinescopeEmbedUrl`.

## 4. Backend API Boundaries

`apps/api` owns all business logic. No direct DB writes from bot or Mini App.

Main folders:

```txt
apps/api/src/
├── main.ts
├── app.module.ts
├── config/env.schema.ts
├── common/
│   ├── guards/internal-token.guard.ts
│   ├── guards/admin-basic.guard.ts
│   ├── filters/http-exception.filter.ts
│   └── money.ts
└── modules/
    ├── health/
    ├── users/
    ├── courses/
    ├── orders/
    ├── payments/
    │   └── yookassa/
    ├── access/
    ├── telegram-auth/
    ├── bot-outbox/
    └── admin/
```

Public API:

```txt
GET  /api/health

POST /api/auth/telegram
body: { initData: string }
returns: { token: string, user: TelegramUserDto }

GET  /api/me/course
auth: Bearer miniapp session token
returns: { hasAccess, course, lessons? }

GET  /api/me/lessons/:lessonSlug
auth: Bearer miniapp session token
returns: lesson with kinescopeEmbedUrl only if access exists

POST /api/orders
auth: Bearer miniapp session token
body: { courseSlug: string }
returns: { orderId, status, paymentUrl } or { alreadyPaid: true }
```

Internal bot API, protected by `X-Internal-Token`:

```txt
POST /api/internal/bot/users/upsert
POST /api/internal/bot/orders
POST /api/internal/bot/orders/:orderId/check-payment
GET  /api/internal/bot/users/:telegramId/course-access?courseSlug=...
GET  /api/internal/bot/outbox?limit=20
POST /api/internal/bot/outbox/:id/sent
POST /api/internal/bot/outbox/:id/failed
```

Webhook API:

```txt
POST /api/webhooks/yookassa/:secret
```

Rules:

- Reject if `:secret !== YOOKASSA_WEBHOOK_SECRET`.
- Parse webhook body and create `WebhookEvent` with key `${event}:${object.id}:${object.status}`.
- Fetch current payment from YooKassa using `GET /payments/{payment_id}`.
- Grant access only when fetched payment is `status=succeeded`, `paid=true`, amount/currency match order, and `metadata.order_id` matches.
- Process duplicate webhooks idempotently: second call returns 200 and does not duplicate access/outbox rows.
- For `payment.canceled`, mark pending order canceled.
- For `refund.succeeded`, mark refunded and revoke access if business chooses refund means revoke.

Admin API, protected by HTTP Basic:

```txt
GET  /api/admin/orders?status=&telegramId=
GET  /api/admin/users/:telegramId/access
POST /api/admin/access/grant
POST /api/admin/access/revoke
```

## 5. Payment Flow

`PaymentsModule` exposes a provider-shaped service, even though v1 implements only YooKassa:

```txt
PaymentProviderService.createPayment(order) -> providerPaymentId/paymentUrl/raw
PaymentProviderService.fetchPayment(providerPaymentId) -> normalized payment
```

YooKassa create payment body:

```json
{
  "amount": { "value": "100.00", "currency": "RUB" },
  "capture": true,
  "confirmation": {
    "type": "redirect",
    "return_url": "https://t.me/YOUR_BOT_USERNAME"
  },
  "description": "Курс: <course title>, заказ <order id>",
  "metadata": {
    "order_id": "<order id>",
    "telegram_id": "<telegram id>",
    "course_id": "<course id>"
  }
}
```

Never grant access from:

```txt
- user clicking "Я оплатил"
- YooKassa return_url
- bot /start after payment redirect
- Mini App opening after payment attempt
```

Grant access only from:

```txt
- verified YooKassa webhook
- backend check-payment endpoint that fetches current YooKassa payment
- admin manual grant
```

## 6. Bot App

`apps/bot` structure:

```txt
apps/bot/src/
├── index.ts
├── config.ts
├── bot.ts
├── webhook-server.ts
├── api/client.ts
├── keyboards.ts
├── handlers/
│   ├── start.ts
│   ├── buy-course.ts
│   ├── check-payment.ts
│   └── commands.ts
└── outbox-worker.ts
```

Bot behavior:

- `/start`: upsert user through API.
- If access exists: show `Открыть курс` as Telegram Web App button.
- If no access: show course description + `Купить курс`.
- `Купить курс`: call API internal create order, then send YooKassa direct `paymentUrl` button and `Я оплатил / Проверить оплату`.
- `Я оплатил`: call API check-payment. If paid, show `Открыть курс`; if pending, tell user payment is still processing.
- Outbox worker: every few seconds polls API outbox, sends Telegram message, then marks sent/failed.
- `/support`, `/terms`, `/paysupport`: must exist before public launch, especially because Telegram payment docs require clear support/terms for purchases.

Production update mode:

- Use Telegram webhook at `POST /telegram/webhook`.
- Validate `X-Telegram-Bot-Api-Secret-Token`.
- Local dev can use polling if `BOT_MODE=polling`.

Rules:

- `layout.tsx` loads `https://telegram.org/js/telegram-web-app.js?62` through `next/script` with `beforeInteractive`.
- `page.tsx` is a client component because it needs `window.Telegram.WebApp.initData`.
- On load: read raw `initData`, call `POST /api/auth/telegram`, keep returned JWT in memory, call `GET /api/me/course`.
- If access exists: show lesson list and Kinescope player.
- If no access: show course preview + buy button that calls `POST /api/orders` and opens `paymentUrl`.
- Do not expose `KINESCOPE_API_TOKEN` to the browser.
- Admin page is minimal and protected by API Basic Auth; it lists orders and supports manual grant/revoke.

## 12. Assumptions Locked For V1

- Content source: DB seed file, not a full CMS.
- Video protection: Kinescope private/domain restrictions in v1; DRM/watermark can be enabled in Kinescope and wired deeper later.
- Admin scope: minimal support admin for orders/access only.
- Redis/BullMQ: not used in v1; PostgreSQL outbox is enough.
- Payment provider: YooKassa implemented now, but DB/API shape leaves room for Telegram Stars because of Telegram’s digital-goods policy.
- Access source of truth: `CourseAccess` in PostgreSQL, written only by API.
